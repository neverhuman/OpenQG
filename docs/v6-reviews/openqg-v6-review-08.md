# Router and proposer loop

The router-native proposer is a real engineering upgrade. `docs/V6-CAMPAIGN-REPORT.md` reports 754 live calls, 65 ok, 649 killed, 28 parse failures, 12 transport failures, and zero empty-output failures. That is a dramatic improvement over the V5 empty-output rate. The code supports the claim: `crates/openqg-bench/src/zyal_genome/proposer_router.rs` uses a strict `ProposalSketch` schema, per-sample mechanism lanes, quality-band rotation, attempt receipts, winner model telemetry, and replayable proposal ledgers. The LLM proposes; `score_proposal` and the deterministic oracle dispose.

The main risk is not schema failure anymore. It is search economics. A 65/754 ok rate means most live calls are spent discovering the current oracle boundary. That can be productive during hardening, but it can also teach the proposer to become an oracle overfitter. `proposer_router.rs::propose_one_sample` explicitly feeds kill reasons back into the repair prompt. For fabricated witnesses, the prompt says the kill message contains the engine-computed value and instructs the model to set the witness to exactly that number. This is transparent and replayable, but it turns a "prediction" into an oracle-filled field.

The lane economics are also uneven. The report says ok yield by lane was `null_diagnostic 25`, `planck_mu0 23`, `free 11`, and `dark_scattering 6`. That is an important signal: the dark-scattering lane is underperforming, and the null-diagnostic lane is producing many survivors. Since the scoring rubric still awards non-data points for derivation, unification, robustness, and parsimony, a null-adjacent derivation can survive without being a good cosmology. V7 should report lane yield by post-V6.1 score, not merely ok/DQ status.

The `ProposalSketch` design in `crates/openqg-bench/src/zyal_genome/proposer_sketch.rs` is a good choice. It flattens serde complexity, pins enum strings from the actual registry, and uses `additionalProperties: false` in the schema. The expander `expand_sketch` is deterministic. But the sketch background still includes `w0` and `wa` as direct fields, while the prompt says background dials cost parsimony and should be certified. This leaves the model with a convenient drift surface. The scorecard charges it, but the proposer still sees it as a first-class lane control.

Memory is better than V5, but still porous. `crates/openqg-bench/src/zyal_genome/proposer_memory.rs::top_scorer_entry` gates top scorers through current `physics_kills`, so old candidates killed by unified physics do not become DO examples. That is good. But it does not re-score with current `score_with_observables`, current covariance, current novelty tiers, or the V6.1 calibration. A record can pass physics and still be an older-rubric reward hack. The memory should only promote entries with a current scorecard receipt under the active rubric version.

Model concentration is another unpriced risk. The report says ok proposals came from three model families: `gpt-oss-120b` 37, `gpt-oss-20b` 19, and `nemotron-3-super` 9. That is enough diversity for an engineering run, but not enough for claims about creative exploration. `winner_model_id` is ledgered, but the scoring does not penalize monoculture or require cross-model rediscovery of a candidate class. V7 should require any promoted mechanism family to be independently rediscovered by at least two model families or one non-LLM generator.

The repair loop also blurs proposal authorship. Router-side structured output repair, client parse repair, and oracle repair are all valuable, but they should create distinct artifact classes. A proposal that only becomes valid after oracle repair should not be equivalent to a first-pass physical proposal. `ProposalAttemptRecord` contains `repair_kind`, `upstream_repairs`, `winner`, `model`, `quality_band`, and `mechanism_lane`. The next step is to feed those fields into score eligibility: an oracle-repaired novel witness should be capped or excluded from novelty.

The league insubstantial-band issue is not fully sealed. The quality bands rotate as `top20`, `any`, `top50`, `any` by default in `RouterConfig`. That can improve yield, but it does not enforce conceptual diversity. The lanes are only four coarse prompts: `planck_mu0`, `dark_scattering`, `free`, and `null_diagnostic`. Since the memory block includes top scorers and DO/DON'T directives, all lanes can converge on the same few registry relations. V7 needs lane-level quotas over mechanism families after expansion, not just prompt labels before generation.

Engineering recommendations: add `active_rubric_version` and `scorecard_sha256` to every memory top-scorer entry. Modify `assemble_memory` to discard entries without a current receipt. Add lane statistics to `run-summary.json`: calls, parse failures, oracle kills, ok, mean score, median score, best current V6.1 score, and post-hoc DQ count. Add a `repair_depth` field to `ScorecardV4` or proposal metadata and cap novelty at zero for oracle-repaired witness values. Finally, add a campaign-level diversity gate: no V7 champion class is promotable unless it appears in at least two independent lanes or is confirmed by a deterministic model-league fit.
