## Data sources and likelihood contracts

The current accessible release is honest about being conservative, but too thin to be scientifically dangerous in a useful way. A three-observable smoke fixture (`h0`, `omega_m`, `sum_mnu`) is useful for plumbing and nothing else (`data/fixtures/smoke/observables.jsonl` lines 6-8). The smoke suite explicitly describes itself as “Tiny committed fixtures for the baseline physics regression,” uses `sm-gr-lcdm-mnu` as baseline, and weights only those three observables (`benchmarks/suites/smoke.yml` lines 6-23). Keep that lane, but rename it internally as `plumbing-smoke`; do not let anyone mistake it for cosmology.

Every real data product needs a likelihood card, not just a JSONL row. Minimum fields: dataset id, release version, citation, license, raw-data access policy, compressed-likelihood provenance, covariance matrix path and checksum, nuisance parameters, masks/cuts, unit conventions, redshift range, validity domain, and known correlations with other datasets. BAO, SNe, CMB compressed parameters, RSD, weak lensing, local-distance-ladder H0, BBN, PTA spectra, LVK stochastic upper limits, and CMB B-mode likelihoods must be separate cards with explicit cross-covariance notes. If cross-covariance is unknown, the league should mark the combined score as provisional, not quietly diagonalize the universe.

Verification must be adversarial. Each likelihood card gets a synthetic recovery test: generate mock data from a known parameter vector, run the engine, and verify recovery within expected uncertainty. It also gets a reference-reproduction test: reproduce at least one published baseline number, such as ΛCDM parameters from Planck-like compressed constraints or a DESI BAO-only distance result, using the exact committed code. For DESI, the relevant near-term source is DR1: the collaboration reports 18.7 million high-confidence redshifts over the first 13 months and identifies dark-energy equation of state, growth, neutrino mass, and inflationary signatures as core objectives (DESI DR1 paper, arXiv:2503.14745). For primordial signals, Planck 2018 remains a required baseline: Planck found no evidence for features beyond a pure power-law primordial spectrum and constrained `r` further when combined with BICEP/Keck (Planck 2018 inflation constraints, arXiv:1807.06211). For nanohertz gravitational waves, NANOGrav 15-year data reports Hellings-Downs-correlated evidence and a characteristic strain amplitude near `2.4e-15` at 1/year under a fiducial SMBH-binary spectrum (NANOGrav 15-year paper, arXiv:2306.16213). These should enter as cited likelihood families, not blog-level facts.

## Forward-model fidelity

The accessible architecture document is a component map, not a physics architecture (`docs/architecture.md` lines 8-24). The repo claims typed manifests, validation helpers, and scoring primitives, but it does not expose a serious cosmological forward model on `main` (`README.md` lines 36-49). A referee will attack this immediately: no Boltzmann solver, no perturbation sector, no transfer functions, no recombination physics, no nonlinear modeling policy, no window functions, no nuisance parameters, no systematics model, no valid way to combine CMB, BAO, SNe, RSD, weak lensing, and GW data.

The fix is a tiered fidelity ladder. Tier 0 remains plumbing. Tier 1 is compressed background/growth: `H(z)`, `D_A(z)`, `D_M(z)`, `D_H(z)`, `r_d`, `fσ8`, distance modulus, and growth index approximations, with explicit validity domains. Tier 2 calls CLASS or CAMB, or consumes frozen emulator tables generated from them, for CMB-derived and matter-power observables. Tier 3 handles candidate-specific perturbation equations or external adapters. A theory cannot enter Tier 2 or Tier 3 unless it provides conservation equations, closure relations, stability checks, and initial-condition handling.

Do not let “derived-not-fit” become theater. Binding a functional form is valuable, but parameter values still need priors, fixed-value provenance, or profiling. `docs/theory-admission.md` already demands unit, meaning, prior/fixed value, and reason for every parameter (`docs/theory-admission.md` lines 17-24). Make that executable: if a candidate adds a fixed `α_i` deviation, the card must say whether the value comes from a derivation, previous measurement, posterior from an independent dataset, or a pre-registered scan. If a value is chosen after looking at the target data, it is fitted, and the league must count it.

The engine also needs vetoes before likelihoods. Veto non-finite predictions, unit mismatches, wrong covariance shapes, superluminal or ghost/gradient instabilities where the model claims an EFT, early-universe energy densities violating BBN/CMB bounds, and theories that fail to recover GR/ΛCDM in the appropriate limit unless explicitly labeled as alternatives with their own baselines. Vetoes should emit machine-readable receipts, not prose findings.

## Statistical rigor

The current scoring primitive is too simple. `gaussian_log_likelihood` returns `-0.5 residual^2 / sigma^2` and ignores normalization (`scoring/likelihood.rs` lines 9-14). `score_metrics` sums that over observables, uses `sigma = max(observable.uncertainty, prediction.uncertainty)`, computes AIC/BIC/MDL, coverage, and a logarithmic parameter penalty (`scoring/likelihood.rs` lines 32-60). The resulting `Scorecard` then sets matched observables as total observables minus invalid findings, which conflates missing predictions, unit mismatches, and other findings (`scoring/scorecard.rs` lines 28-37). This is fine for a smoke test; it is not a model-selection engine.

Replace this with four explicit score layers. First, a strict validation layer: schema, units, finite values, domains, covariance dimensions, provenance, and declared nuisance treatment. Second, a likelihood layer with full covariance support: `-0.5(r^T C^{-1} r + log det C + n log 2π)` for Gaussian compressed likelihoods, plus plug-in adapters for non-Gaussian likelihoods and upper-limit constraints. Third, a fitting/profiling layer: fixed parameters, profiled nuisance parameters, posterior samples, and nested-sampling evidence must be distinct. Fourth, a decision layer: Δχ², ΔlogL, AIC, BIC, approximate/true evidence, posterior predictive checks, and calibration against decoys.

No single scalar should promote a theory. Promotion requires a score vector: predictive gain over the correct baseline, parameter cost, robustness under dataset removal, calibration on mocks, physical-veto status, and novelty. A theory that improves H0 by breaking CMB or growth must fail. A model that wins only when covariance is omitted must fail. A model that uses a hidden nuisance knob but reports it as derived must fail.

The league must separate discovery and evaluation data. Use “proposal data” to generate ideas and “frozen evaluation data” to score. Rotate withheld slices only through a governance event, not every run. Require pre-registration for new model families: parameters, priors, allowed datasets, and expected observables must be declared before the first score. This is how OpenQG avoids becoming an automated p-hacking machine.

## Theory coverage and the unified-physics target worth chasing

The project name implies quantum gravity, but a data-driven engine cannot adjudicate quantum-gravity programs as identities. String theory, loop quantum gravity, causal dynamical triangulations, asymptotic safety, and causal sets mostly do not make unique, discriminating, near-term cosmological predictions at the level needed for an automated league. The implicit verdict should be: admit them only through falsifiable low-energy handles. Examples include a running or stochastic effective Λ, specific primordial-spectrum features, bounce signatures, cosmic-string/superstring stochastic gravitational waves, fixed EFT deviations, tensor-to-scalar predictions, non-Gaussianity templates, Lorentz-violation bounds, equivalence-principle tests, black-hole-ringdown deviations, or modified propagation of gravitational waves.

The strongest near-term target is not “quantum gravity” in general; it is the early-universe relic sector: primordial tensors, primordial non-Gaussianity/features, and stochastic gravitational-wave backgrounds from cosmic strings/superstrings, phase transitions, scalar-induced perturbations, or bounce/inflation alternatives. This target has the best ratio of foundational significance to scoreable data because it connects high-energy physics to observable spectra across CMB B-modes, PTA nanohertz data, LVK ground-based stochastic searches, and future LISA frequencies. String-inspired cosmic superstrings currently offer the cleanest QG-adjacent handle because they can predict a network-generated stochastic gravitational-wave spectrum and CMB/string-tension constraints. Loop quantum cosmology offers scoreable bounce/feature templates, but the mapping from full LQG to a unique prediction is weaker. Causal sets have an interesting fluctuating-Λ/dark-energy handle, but present scoreability is mostly background-level and degenerate. Asymptotic safety is intellectually important, but current cosmological signatures are usually mediated through model-building choices rather than unique predictions.

The concrete 2-5 year flagship program should be `early-relic-gw-spectrum`. Encode a family of templates with parameters such as string tension `Gμ`, reconnection probability `p`, loop-size prescription, spectral turnover/break frequencies, reheating temperature proxy, equation-of-state episode, primordial tensor amplitude `r`, tensor tilt `n_t`, scalar feature amplitude/frequency, and non-Gaussianity parameters where relevant. Score against: Planck/BICEP/Keck and successor CMB constraints on `r`, `n_s`, running, features, and non-Gaussianity; NANOGrav/EPTA/PPTA/CPTA PTA spectral amplitudes and spatial-correlation evidence; LVK O1-O4 stochastic upper limits and astrophysical foreground models; future LISA mock likelihoods; CMB string-tension limits; and BBN/CMB integral bounds on total gravitational-wave energy density.

The belief-moving observables are clear. A scale-consistent stochastic background across PTA and LISA/LVK bands with spectral breaks matching a relic-network or phase-transition model would matter. A primordial B-mode detection with compatible tensor tilt and no fatal foreground/systematic failure would matter. A repeated null tightening `r`, `Gμ`, and stochastic background energy density would also matter by killing large parts of theory space. The engine should express all three outcomes honestly: discovery, narrowing, or death.

Do not make dark energy the flagship unification target. DESI’s evolving-dark-energy hints are important and scoreable, but background-level `w0-wa` freedom is too degenerate and too easy to overfit. Dark-sector models belong in the league, especially as baselines/competitors, but they should not be sold as the central QG target unless they provide a derived, fixed low-energy handle and survive growth, CMB, BAO, SNe, and local tests.

## ZYAL multi-agent design

The accessible repo has the beginnings of a runbook preview type: file, id, job name, arming state, research flag, permission summary, stop summary, validity, strict validity, and warnings (`types/zyal.rs` lines 8-20). That is useful metadata, but not enough. The architecture should be: LLMs propose; Rust host disposes. Rust owns durable policy, config, tar validation, path allowlists, secrets exclusions, receipts, run contracts, schema validation, score execution, and promotion rules. TypeScript owns dashboards and browser surfaces only. The browser must never be a source of truth for scores, policy, or run state.

ZYAL should operate on claim graphs, not essays. A candidate theory becomes a set of claims: derivations, equations, parameters, priors, adapters, predictions, likelihood bindings, and falsifiers. Each claim has dependencies and executable obligations. Agents can suggest a claim or repair a failed claim, but the host must decide whether the obligation was satisfied by a deterministic checker, symbolic algebra, unit checker, numerical solver, formal proof fragment, or frozen dataset comparison. “Judge council” language is not enough; model judges can route and summarize, but they cannot certify physics.

Anti-Goodhart mechanics must be built in. Use hard baselines and decoys in every generation. Delay reward: an agent gets credit only when later independent checks confirm usefulness. Keep a novelty archive, but do not reward novelty that evades observables. Require external-oracle diversity: a claim that passes only an LLM review and no numeric/symbolic/data test remains speculative. Red-team agents should generate falsifiers and decoys, not merely criticize prose.

For archive hardening, implement a review-pack contract. A valid review invocation should include an archive hash, file manifest, extraction root, selected-path list, and expected artifact contract. The host should verify tar safety: no absolute paths, no `..`, no symlink escapes, no device files, no private local paths, no runtime state, no secrets, no downloaded archives, no logs, and no receipts unless explicitly requested. The output pack for this task should have exactly one file, root-level `engineering-spec.md`; that rule belongs in Rust, not in a prompt.

## Software, reproducibility, and release gates

The repo already has the right cultural instincts. The README directs users to `just setup`, `just fast`, `just check`, `just security`, `just release-check`, and `jankurai audit` (`README.md` lines 22-34). Governance names ownership boundaries and generated-output directories (`GOVERNANCE.md` lines 8-24). The problem is not attitude; it is missing executable specificity.

Make the proof lane map to scientific claims. `just fast` should run unit and schema tests. `just physics-smoke` should validate toy fixtures. `just cosmology-regression` should reproduce reference ΛCDM scores. `just league-smoke` should run a tiny model league with baselines and decoys. `just flagship-mock` should run the early-relic mock challenge. `just release-check` should fail if any promoted score lacks a receipt, any dataset lacks covariance/provenance, any candidate has anonymous knobs, or any generated artifact is stale.

Add stable artifacts: `scorecard.json`, `likelihood-receipt.json`, `fit-receipt.json`, `dataset-card.json`, `candidate-card.json`, `claim-graph.json`, `veto-receipt.json`, and `release-manifest.json`. Each receipt must include source commit/archive hash, command, environment summary, random seed, input hashes, output hash, schema version, and validity status. This is not bureaucracy; it is how a serious physicist reruns the result.

Finally, make documentation subordinate to code. The prompt describes a sophisticated background+growth/theory-league engine, but the accessible source on `main` is a much smaller release. That mismatch is exactly the kind of trust failure OpenQG claims to prevent. The next release should include an automatically generated “source truth table” listing every documented capability, the code path implementing it, the tests proving it, and the receipt from the last successful run. If a capability is aspirational, label it aspirational. If it is implemented only for smoke fixtures, label it smoke-only. A stern reviewer will forgive honest limitations; they will not forgive a system that sounds more complete than it is.
