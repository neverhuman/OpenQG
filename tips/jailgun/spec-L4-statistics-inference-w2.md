# OpenQG / ZYAL Statistical Honesty Engineering Specification

## Ranked backlog

This backlog is written against the file paths and claims named in the review request. The requested `source.tar.gz` was not present in the sandbox filesystem, and connected/public searches did not expose the curated snapshot; therefore this is a constrained engineering specification, not a line-by-line audit of unavailable file contents. The priority ordering below assumes the documented system shape: `docs/architecture.md` defines a background-plus-growth forward model; `docs/theory-league.md` and `crates/openqg-core/src/theory/league.rs` implement profile-fit, AIC/BIC, and an approximate ln-evidence; `crates/openqg-core/src/scoring/covariance.rs` and `crates/openqg-core/src/scoring/likelihood.rs` govern the likelihood; and `docs/ZYAL.md` describes an LLM-propose / deterministic-host-judge orchestration boundary.

## Data sources and likelihood contracts

The current target files named in the request imply a small cosmology fixture set: `data/fixtures/cosmology/tier0-combined.jsonl`, `growth-rsd.jsonl`, and `sh0es-h0.jsonl`. Those are appropriate for engine smoke tests, but they are not enough for a referee-grade cosmology league unless every row is converted into a likelihood object with provenance and covariance. The core change is conceptual: OpenQG should stop treating data rows as independent observations and start treating each probe as a published likelihood with a data vector, covariance, nuisance parameters, masks, units, redshift definitions, and independence assumptions.

Minimum row metadata should include source publication, measurement release, observable definition, redshift or effective scale, units, calibration assumptions, covariance block ID, nuisance parameter links, and whether the row is valid for background-only, linear-growth, nonlinear-growth, CMB, lensing, gravitational-wave, or local-distance-ladder inference. The engine should reject final-tier comparisons when a row has no covariance block or when the covariance block is inconsistent with the active mask. If a fixture is intentionally diagonal for testing, the report must call it “smoke-test likelihood” and keep it out of headline model ranking.

The SH0ES-H0 fixture deserves special handling. A local H0 Gaussian row is valuable as a tension probe, but it should not be casually merged with BAO/CMB-derived or inverse-distance-ladder constraints unless the model class and likelihood explain what is being combined. A late-time model can relieve or worsen H0 tension differently depending on the sound horizon, supernova calibration, and early-universe assumptions. A single H0 row can dominate a small fixture league and make an evolved model look profound when it has merely learned a tension direction. The fix is to tag SH0ES as a named stress probe and require both “with SH0ES” and “without SH0ES” rankings, plus per-probe residuals.

For growth-RSD data, the likelihood must encode whether values are fσ8, AP-distorted fσ8, E_G, weak-lensing S8-like constraints, or compressed combinations. The forward model must state whether it computes scale-independent linear growth, includes massive neutrinos, applies survey window functions, and handles Alcock-Paczynski dependence. A row-level JSONL fixture cannot carry all of that by itself; it needs a companion likelihood manifest. If the current `scoring/likelihood.rs` treats all rows as Gaussian residuals, that should remain a test harness only.

The data split should be hard. Use a discovery tier for evolved candidates, a calibration tier for gate tuning and anchor calibration, a validation tier for candidate-family selection, and a final referee tier for one-time unblinding. The final tier should be inaccessible to LLM prompts, mutation operators, and dashboards during search. ZYAL receipts should prove which hashes were visible to each lane. Without this split, evolutionary search turns even honest likelihoods into a reusable training set.

## Forward-model fidelity

The architecture described in `docs/architecture.md` and implemented through `crates/openqg-core/src/cosmology/background.rs`, `growth.rs`, and `forward.rs` is an honest starting point if it says “background plus growth only.” It is not adequate for broad cosmology or quantum-gravity-adjacent claims. A background solver can compute H(z), distances, and simple expansion observables. A growth solver can estimate linear growth under restricted assumptions. But a referee will attack any result that uses this machinery to rank models whose real signatures live in CMB anisotropy spectra, matter power spectra, weak-lensing kernels, massive-neutrino degeneracies, nonlinear clustering, early dark energy, or coupled dark-energy perturbations.

The forward model needs a capability matrix. Each candidate prediction should declare which observables it can score: background distances, local H0, linear fσ8, BAO compressed distance ratios, CMB distance priors, full CMB spectra, weak lensing, standard sirens, or gravitational-wave propagation. A row is scoreable only if the candidate and engine cover the required physics. Unsupported rows should remain explicit refusals rather than being approximated silently. This preserves the project’s strongest principle: refusal is better than fake coverage.

The minimum referee-grade improvement is a validation bridge to an external Boltzmann and perturbation solver such as CLASS or CAMB. The Rust core does not need to become a Boltzmann code immediately, but `forward.rs` should be able to compare its restricted approximations against a trusted solver over a grid of LCDM and simple wCDM parameters. For any model beyond those domains, OpenQG must either implement the perturbation equations and validate them or mark those rows unsupported. This is especially important for EDE and coupled-DE, which the prompt already admits are not yet scoreable.

Numerical verification should become part of the scientific receipt. For each forward-model component, require unit tests for limiting cases, conservation laws, monotonicity where physically required, derivative stability, tolerance under step-size changes, and agreement with a reference implementation. Growth solvers should test LCDM growth against known approximations but not use those approximations as substitutes for validation. Background solvers should test curvature, radiation, massive-neutrino assumptions, and redshift-unit handling explicitly. Any failure in a domain should propagate to the league as “not scoreable,” not as a zero residual or missing row.

## Statistical rigor and model ranking

The central statistical issue is whether `docs/theory-league.md`, `crates/openqg-core/src/theory/league.rs`, `crates/openqg-core/src/scoring/covariance.rs`, and `likelihood.rs` can support trustworthy model ranking. Profile likelihood plus AIC/BIC plus Schwarz/Laplace ln-evidence is acceptable for development triage. It is not enough for a referee-grade ranking after search.

AIC estimates expected predictive information loss under regularity assumptions and large samples. BIC approximates a Bayes factor under stronger assumptions, including large sample size, regular models, and specific prior behavior. The Schwarz/Laplace approximation can be useful when the posterior is near-Gaussian, interior to prior bounds, identifiable, and well described by local curvature. Cosmology model comparison often violates those assumptions: degeneracies, parameter boundaries, non-Gaussian tensions, nuisance priors, compressed likelihoods, and multimodal posterior structure are common. An evolutionary candidate generator makes the situation worse because the model was selected after repeated attempts to improve the same score.

Therefore, OpenQG should adopt a bright-line policy. AIC/BIC and approximate ln Z are “league-dev metrics.” A “referee-grade evidence” requires explicit priors, nuisance parameters, data masks, covariance, sampler settings, convergence diagnostics, posterior samples, and evidence estimates from nested sampling, thermodynamic integration, SMC, or another auditable marginal-likelihood method. If that is too expensive for every mutant, use cheap metrics for triage and run full evidence only for promoted candidates, all relevant baselines, and decoys.

The correction that “the +36.7 was an artifact” is directionally right if it means the old comparison failed to refit the baseline, omitted covariance, and ignored complexity. A baseline must be fit under the same rules as the challenger: same data vector, same masks, same covariance, same likelihood, same nuisance model, same parameter constraints, and same optimization budget. A fixed LCDM baseline compared against a tuned extension is not a fair model comparison. A diagonal covariance can overstate independent information. A missing complexity penalty can turn flexible curve fitting into a false discovery. Correcting those errors is not optional housekeeping; it is the minimum condition for a meaningful Δ score.

But the new ΔAIC or Δln Z can still mislead. First, if the likelihood is a Gaussian approximation to a non-Gaussian published constraint, the delta inherits that approximation error. Second, if evidence is computed by a Schwarz approximation rather than actual marginalization, prior-volume and degeneracy effects may be wrong. Third, if the model was evolved against the same data, the apparent improvement is post-selection biased. Fourth, if the data vector mixes probes with hidden correlations, the covariance can still be incomplete even when a matrix is present. Fifth, if nuisance parameters are optimized but not counted or marginalized, complexity is under-penalized. The report should say all of this explicitly whenever it shows a development delta.

Absolute goodness-of-fit must precede relative ranking. For each promoted model, report χ² or deviance by probe, posterior predictive p-values or simulation-calibrated discrepancy measures, standardized residuals, and the worst residual rows. A candidate that improves over LCDM by ΔAIC while failing a major probe is not a discovery; it is a model inadequacy map. The league should have a hard gate: no “winner” label unless absolute fit clears pre-registered thresholds on the combined data and on critical probe families.

Ranking uncertainty should be a first-class output. Report not only best-fit parameters and Δ scores but also the probability of each rank under data resampling, covariance perturbation, prior sensitivity, nuisance choices, and search replay. A simple initial implementation can bootstrap rows within probe-appropriate blocks, jackknife probes, and rerun evidence on top candidates. A mature implementation should use simulation-based calibration: generate mock universes from LCDM and known alternatives, run the full ZYAL evolutionary search, and measure how often the engine falsely promotes a beyond-LCDM candidate. This directly estimates the false discovery behavior of the whole system, not just the optimizer.

Parameter accounting is another likely referee attack. “Derived-not-fit” binds the functional form, but it does not automatically derive numerical parameter values. If an agent chooses a potential shape, a prior range, a threshold, a transition redshift, a coupling, a veto constant, or a data mask after seeing scores, that choice is a parameter or a search degree of freedom. The parameter manifest should distinguish physical parameters, nuisance parameters, hyperparameters, discrete family choices, calibration constants, fixed literature constants, and genuinely derived quantities. Complexity penalties and evidence priors should include all degrees of freedom that influence predictions.

The minimum statistical apparatus before a result deserves referee trust is: frozen data tiers; full covariance likelihoods or explicit non-promotable labels; equal baseline and challenger fitting; explicit priors; nuisance marginalization; nested/SMC evidence for promoted candidates; absolute goodness-of-fit; multiplicity correction across search; decoy calibration; blind final evaluation; and ranking uncertainty. Anything less can still be valuable engineering, but the report must call it exploratory.

## Theory coverage and the best attainable unified-physics target

The project’s strongest stance is its refusal to claim new physics. Preserve that. The archive description already admits background-plus-growth only, no Boltzmann CMB, diagonal-vs-covariance limitations, analytic-only unification, derived-not-fit limits, and unscoreable EDE/coupled-DE. Those limitations should be enforced in code and reports, not merely documented in `docs/architecture.md` or `docs/zyal-next-level-design.md`.

For a data-attainable “unified physics” target, do not start by trying to score full quantum gravity. The highest-value target is a constrained gravity/dark-sector effective theory that links expansion, growth, lensing, and gravitational-wave propagation through one action-level parameterization. In plain terms: chase a falsifiable modified-gravity / EFT-of-dark-energy lane, not a grand unification headline. The target should derive a small set of equations for H(z), the effective Newton constant, gravitational slip, tensor speed or tensor friction, and distance propagation, then confront them with BAO/SN/H0, RSD, weak-lensing summaries where valid, and gravitational-wave constraints where valid. This is not “theory of everything”; it is the scoreable frontier where real data can punish a model.

The falsifiable program should be narrow. Define one action class, for example a stable scalar-tensor or Horndeski/EFT-of-DE subset consistent with gravitational-wave speed constraints. Derive the background equations, perturbation equations, stability conditions, limiting LCDM behavior, and observable maps. Declare all free functions and parameterizations before data access. Validate against a Boltzmann solver that supports the class or explicitly restrict to rows the in-house solver can compute. Score against frozen data with priors chosen from physical stability and literature, not from leaderboard tuning. Failure criteria should include unstable perturbations, no LCDM limit, inability to fit background and growth simultaneously, or reliance on a single tension row.

This target is worth chasing because it is physically meaningful, falsifiable, and data-connected. It also exposes the engine’s weakest statistical muscles: correlated probes, nuisance parameters, degeneracy, prior sensitivity, and tension-aware reporting. If OpenQG can handle that honestly, it earns credibility. If it cannot, more ambitious “unification” scoring will look like theater.

For analytic unification modules such as `theory/unification.rs`, maintain a separate structural score. Structural claims may be valuable when they derive gauge content, symmetry constraints, or limiting behavior, but they should not be conflated with empirical model evidence unless they emit scoreable predictions with parameter provenance. A theory that explains form but not constants should receive form credit, not hidden empirical credit. A theory that only predicts null deviations should be evaluated against null tests, not granted broad cosmology coverage.

## ZYAL multi-agent design

The LLM-proposes / deterministic-host-judges boundary in `docs/ZYAL.md` is the right architecture. The danger is not that agents are creative; the danger is that creativity plus repeated scoring becomes a high-dimensional overfitting machine. ZYAL should therefore treat search pressure as a statistical contaminant and manage it with the same seriousness as fixture leakage.

Every ZYAL run should have a signed run contract: accessible files, hidden files, model family, mutation operators, scoring budget, stopping rule, allowed priors, parameter budget, and promotion threshold. Agents should never see final-tier scores during candidate generation. Prompt text, candidate text, derived equations, parameter manifests, and score receipts should be hashed. Negative memory should record failed concepts and why they failed, but it must not leak final-tier information back into the search loop.

The anchor and adversary system should be empirically calibrated. `anchors.rs` should include known-good LCDM and simple wCDM cases, known-bad curve-fitting cases, covariance-abuse cases, baseline-not-refit cases, leaked-fixture cases, hidden-parameter cases, and physically unstable cases. `adversary.rs` should attempt to smuggle target values, exploit missing covariance, split one physical parameter into several uncounted knobs, or optimize masks. The system should publish gate confusion matrices: how often it rejects valid models and how often it admits invalid ones.

ZYAL should also separate roles. Proposal lanes can be creative; derivation lanes must formalize equations; implementation lanes must map observables; statistics lanes must define likelihood and priors; red-team lanes must attack leakage and overfitting; judge lanes must be deterministic and receipt-bound. The final judge should not be another free-form LLM opinion. It should be a deterministic checklist plus optional human-readable critique generated only after the receipts are fixed.

## Software and reproducibility

The Jankurai boundary in the prompt is correct: Rust should own durable policy, config, tar validation, receipts, and run contracts; TypeScript should own browser and dashboard surfaces. For OpenQG, that means the scientific kernel must not depend on dashboard state, local overrides, hidden prompts, downloaded archives, or mutable runtime files. A result should be reproducible from a manifest, a source hash, a data hash, a candidate hash, a likelihood hash, a seed set, and an environment declaration.

The Rust core should make unsafe scientific states unrepresentable where possible. A promoted `LeagueResult` should require a covariance receipt, baseline refit receipt, parameter manifest, prior manifest, evidence method, goodness-of-fit report, and data-tier receipt. Missing covariance should not be represented as an empty matrix with diagonal fallback in final mode. Unsupported observable rows should be a typed refusal, not an absent residual. Nuisance parameters should have types and priors. Search degrees of freedom should be counted or explicitly redlined.

Reproducibility tests should include golden fixture tests, mock-universe tests, cross-solver tests, and adversarial regression tests. Golden tests ensure stable output on small fixtures. Mock-universe tests measure false discovery and rank calibration. Cross-solver tests compare `background.rs`, `growth.rs`, and `forward.rs` with reference solvers where applicable. Adversarial tests encode known historical failures: unfair baseline, diagonal covariance, uncounted parameters, leaked constants, masked bad rows, unstable physics, and final-tier reuse.

The report generator should be strict about language. It should not allow a development run to say “evidence favors” when it used AIC/BIC or a Schwarz approximation. It should not allow a background-only run to imply CMB validation. It should not allow a structural unification score to imply empirical success. It should label each result as one of: smoke test, development triage, validation run, blinded final run, or referee-grade evidence run. This is not cosmetic. It is how the project maintains the difference between honest engineering and accidental hype.

## Acceptance definition

A result from this engine deserves a referee’s trust only when the following are true: the data tier was frozen before search; the candidate family and priors were pre-registered; the forward model covers the scored observables; covariance and nuisance parameters are handled consistently; the baseline and challenger are refit under identical rules; full evidence is computed for promoted candidates and baselines; absolute goodness-of-fit is acceptable; search multiplicity is measured; decoys calibrate false promotion; the final run is blinded or one-time unblinded; and the report includes rank uncertainty and forbidden-claim language.

Until then, OpenQG can still be a valuable theory-discovery engine, but its honest claim should be narrower: it can generate, veto, and triage candidate physics under explicit limitations. That is already useful. The next engineering milestone is to make the statistical firewall strong enough that a skeptical cosmologist cannot dismiss the league as an optimizer trained on its own benchmark.
