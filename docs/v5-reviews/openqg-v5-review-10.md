# Memory and data-brief loop

`crates/openqg-bench/src/zyal_genome/proposer_memory.rs` is useful and dangerous for the same reason: it turns run history into future proposer priors. `build_data_brief` computes real pulls against Planck LCDM using `BackgroundForwardModel`, then prints a directive: "GOAL: reduce the largest |pull| WITHOUT inflating the others." If growth pulls are negative, it adds "growth must be SUPPRESSED (G_eff/G < 1, e.g. planck_mu0_geff with mu0 < 0), not enhanced." That is factually aligned with the admitted fixture, but it narrows the search.

The campaign report says 49/49 live proposals aimed at suppressed growth. That is too much convergence for a theory-discovery engine. It suggests the prompt stack converted a data diagnosis into a monoculture: the LLM repeatedly emits the same phenomenological `mu0` idea because the brief and memory make it the safest route through the oracle. Jekko best-of-K then amplifies the same class because samples are pre-scored by `score_proposal`.

Memory poisoning risk is real. `assemble_memory` reads every `proposal-ledger.jsonl` and `proposal-attempts.jsonl` under `runs_root`, extracts top scorers, normalizes kill reasons by substring, and renders DO/DON'T lines. If a flawed candidate class scores well because of a current scoring bug, it can enter `TOP SCORERS` and become prompt advice for later chunks. The V5 h/Omega_m/alpha champion should not be used as a positive memory item, because it passes only because adjudication and parameter-cost gates are incomplete.

Mitigation 1: memory must be promotion-gated. Only candidates that pass `run_veto_cascade`, `adjudicate`, covariance likelihood, and background-parameter provenance should be eligible for `TOP SCORERS`. Until V6 wiring exists, mark all memory-derived top scorers as "diagnostic, not trusted" or omit them. Implement this in `proposer_memory.rs::top_scorer_entry` by requiring a ledger field like `promotable=true`.

Mitigation 2: memory needs diversity accounting. Store and render counts by mechanism family: `planck_mu0`, `dark_scattering`, `interacting_de`, `massive_neutrino`, `early_dark_energy`, `ndgp`, `fr`, `alpha_basis`, `null_diagnostic`. Add a directive when one family dominates: "DO: propose a mechanism outside the current top family." This should be deterministic and auditable, not left to prompt vibes.

Mitigation 3: DO/DON'T lines should distinguish physics facts from current-oracle facts. "Enhanced growth worsens the admitted f_sigma8/S8 fixture" is a data fact. "Only registry relations verify" is an oracle fact. "planck_mu0_geff with mu0 < 0" is a vocabulary hint, not a mechanism recommendation. Render these under separate headings so the LLM does not confuse a scoring vocabulary with a physical explanation.

Mitigation 4: protect against ledger injection. Ledgers are generated by the engine, but if a malformed or external ledger lands under `runs_root`, `assemble_memory` will parse permissively and include its records. Add a run-level signature or at least a schema/version check before a record can affect memory. Require `record_kind` to be known, `scorecard_sha256` or proposal hash to be present, and the run config hash to match the current scoring version.

Mitigation 5: make the data brief covariance-aware. The current brief reports pulls using per-record `uncertainty`. Once `LikelihoodData` is wired, a correlated block does not have independent one-dimensional pulls. Print whitened residuals for covariance blocks: `L^-1 r`, ordered by absolute whitened component, and label block tension rather than independent sigma pulls. Otherwise the prompt will overemphasize correlated points.

Mitigation 6: include negative examples of overfit parameter drift. The memory should tell the proposer that moving `h`, `omega_m`, or `w0` without a mechanism is not a theory. That requires V6 to first classify those as costed or invalid. Then memory can say: "DON'T: rely on unprovenanced background drift; it now costs/freezes unless derived."

The goal is not to remove memory. The goal is to make memory a curriculum with guardrails: it should help the proposer avoid repeated invalid outputs while preserving multiple scientific hypotheses. Right now it is too close to an exploit cache for the current rubric.
