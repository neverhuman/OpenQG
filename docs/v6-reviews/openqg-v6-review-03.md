# The anchor calibration

The V6.1 anchor calibration is necessary, but not sufficient. `crates/openqg-core/src/cosmology/forward.rs::BackgroundForwardModel::compute` adds `CMB_LA_ANCHOR_CALIBRATION` to `c.cmb_acoustic_scale()` and `CMB_R_ANCHOR_CALIBRATION` to `c.cmb_shift_r()`. The constants are defined as published Planck-2018 distance-prior values minus the engine's raw predictions at `CosmologyParams::planck_lcdm()`: raw `lA = 302.225598` versus published `301.471`, and raw `R = 1.749003` versus published `1.7502`.

This directly fixes the headline V6 failure. The archive says the engine's `cmb_lA` had a +0.755 bias, roughly 8.4 sigma under the compressed Planck prior, and that the optimizer harvested about 35 nats by drifting `h`. The regression test `forward.rs::v61_calibration_guard::calibrated_anchor_matches_planck_distance_priors` confirms the calibrated model hits the Planck anchor within a small fraction of the quoted sigmas. That is a good guard against reintroducing the same constant anchor error.

The remaining question is functional form. A constant offset assumes the fitting formula's error is independent of the cosmology. That is not established anywhere in the archive. The raw `cmb_acoustic_scale()` and `cmb_shift_r()` depend on `z_star`, `sound_horizon`, `angular_diameter_distance`, and the engine's simplified background physics in `crates/openqg-core/src/cosmology/background.rs`. If the fitting-formula residual changes with `h`, `omega_m`, `omega_b_h2`, `n_eff`, curvature, or CPL dark energy, subtracting the Planck-anchor residual merely moves the exploit off-anchor. V6 found the constant term. V7 should expect the next campaign to find slope or curvature terms.

This matters because the compressed Planck priors have small errors. The `cmb_lA` uncertainty quoted in the regression guard is 0.090. A residual of only 0.18 two or three sigmas from the anchor is already a 2 sigma model-bias term. In a covariance block, that residual can couple to `R` and `omega_b_h2`, so the likelihood impact is not just one diagonal pull. `crates/openqg-core/src/scoring/covariance.rs::score_metrics_cov` correctly handles the covariance block, but it cannot distinguish physical residuals from forward-model residuals.

The current test also does not probe derivatives. The degeneracy-valley regression in `crates/openqg-bench/src/zyal_genome/physics_score.rs::v6_covariance_tests::covariance_mode_is_recorded_and_the_compressed_cmb_cannot_close_the_valley` constructs one drift direction with `h = 0.7176`, `omega_m = 0.2822`, and `w0 = -1.144`. That is valuable, but it is not a calibration validation grid. It asserts the known valley is now closed; it does not show the calibrated distance priors remain unbiased over the optimizer's allowed prior box.

The right short-term V7 fix is an explicit calibration-residual envelope. Add a small table of Boltzmann reference points around the Planck anchor, covering at least independent perturbations in `h`, `omega_m`, `omega_b_h2`, `n_eff`, `w0`, `wa`, and `omega_k`, plus the known V6 valley direction. Implement this as a new fixture consumed by `forward.rs` tests. The guard should check not only anchor values but residuals and derivatives: `abs(delta_lA) < 0.25 sigma`, `abs(delta_R) < 0.25 sigma`, and finite-difference slopes matching the reference within a stated tolerance. If that cannot be met, the compressed CMB likelihood should be downgraded or excluded from campaign scoring until a Boltzmann backend lands.

The long-term fix is to stop treating compressed CMB priors as background-only truth for modified cosmology. Add a `ForwardKind::Boltzmann` implementation behind `crates/openqg-core/src/cosmology/forward.rs::ForwardModel`, likely through CLASS or hi_class. The `ForwardManifest` type already has a `Boltzmann` variant and a `provenance_hash` field. Use it. The Planck distance-prior block should become a compatibility smoke test, not the core CMB likelihood. A V7 campaign may still use the calibrated background model for cheap triage, but any promoted candidate should be rescored through a Boltzmann-backed distance-prior or spectra path before it receives data-fit credit.

Engineering spec: keep `CMB_LA_ANCHOR_CALIBRATION` only as a stopgap and stamp a calibration version in the scorecard. Add a `cmb_calibration_mode` or `forward_manifest` field to `DataFitOutcome` or the campaign receipt. Add a regression that fails when a scorecard uses `LikelihoodMode::Covariance` with Planck compressed priors but no calibration-envelope proof. This prevents the next archive from claiming "calibrated" when only the anchor, not the neighborhood, has been checked.
