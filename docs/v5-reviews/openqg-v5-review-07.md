# The jekko loop

`crates/openqg-bench/src/zyal_genome/proposer_jekko.rs` is a strong operational upgrade. The old failure mode was invisible provider output and silent parse collapse. V5 records each `ProposalAttemptRecord`, distinguishes `empty_output` from `parse_error`, includes stderr excerpts for transport failures, and tests the transport behind an injected `LiveCaller`. The best-of-K design also makes practical sense for a flaky free-token provider.

The main risk is that oracle-repair turns the deterministic scorer into an overfitting teacher. `oracle_repair_prompt` includes exact `kill_reasons` and asks the model to "Fix ONLY these violations; keep everything else." That makes the proposer learn the current oracle surface, not the physics. This is acceptable for syntax and evidence-binding repairs, but risky for physics kills. A model can converge on minimal strings or provenance labels that satisfy current substring checks without improving mechanism quality. The V5 champion class illustrates the broader pattern: it learns to carry `screening="vainshtein"` because triage accepts a screening string, while `adjudicate` would reject missing `screening_recovery` if wired in.

Mitigation: split repair classes. Parse repair may include raw parse errors. Evidence repair may say which cited paths are missing. Physics repair should not quote full kill-reason internals; it should give a stable public rubric category and require a fresh proposal, not a patch. For example: "Your screening claim is not quantitatively checkable; provide a numeric recovery derivation or remove the modified-gravity claim." Do not expose exact thresholds except in documentation.

Best-of-K selection introduces another bias. `propose_one_sample` scores every sample with `score_proposal` and `propose` returns the highest non-disqualified total. That means the live proposal distribution is filtered by the same flawed scorecard before entering evolution. If half novelty, free background drift, or unwired adjudication are exploitable, best-of-K amplifies them. Mitigation: log not only the winner but the full candidate score distribution, and periodically inject a random non-disqualified sample rather than always the best. Add diversity constraints over relation names, mechanism class, and changed observables.

Provider-failure handling is better but still compresses useful information. The attempt record stores `raw_sha256` and `raw_len`, not raw stdout. That is probably correct for prompt/privacy hygiene, but replay/debugging cannot reconstruct parse failures from the ledger alone. The full winning proposal is recorded in `LiveProposalRecord.doc`; failed raw outputs are not. For internal debugging, store a redacted parse-error excerpt or a structured parse-failure reason tree, not the full prompt/output. The current `truncate_raw` in repair prompts is useful at runtime but not persisted.

The memory loop compounds the jekko bias. `proposer_memory.rs::build_data_brief` explicitly says "growth must be SUPPRESSED (G_eff/G < 1, e.g. planck_mu0_geff with mu0 < 0)." That is a good data-derived hint, but when combined with `assemble_memory` top scorers and DO/DON'T lines, it can collapse the proposal population. The campaign report says 49/49 live proposals aimed at suppressed growth. That is not just success; it is monoculture. V6 should request mechanism diversity explicitly: at most N proposals per relation family per run chunk, or prompt slots assigned to "phenomenological mu0", "dark-sector momentum exchange", "massive neutrino/growth normalization", "early-time sound-horizon", and "null diagnostic".

The quality-band routing is another reproducibility caveat. `default_caller` sets `JEKKO_RUN_QUALITY_BAND` from config, but the white-paper report records a deterministic replay only from ledgers, not from provider state. That is fine, but V6 should stamp proposer config into `ProposalAttemptRecord`: command, quality band, sample count, repair budget, timeout, and prompt template hash. Without this, a referee can replay scoring but not understand the live sampling environment.

Finally, the preflight should test more than "can the provider return bytes." It should parse, score, and intentionally trigger one repair against a harmless fixture. The current architecture supports this; add a `jekko selftest` using a local caller and a live smoke prompt whose expected schema is small. This will catch provider markdown drift and empty-output bursts before a multi-hour campaign.
